# 《记仇的 NPC：铁匠阿铁》设计说明

## 1. 创意

一个会记仇的铁匠 NPC。玩家每回合只有两种选择：**恶作剧** 或 **帮忙**。

关键不在"对话有多自然"，而在于**这个 NPC 真的记得你**：

- 你在会话 A 里把阿铁的风筝踩进泥里，他嘴上不说，心里记下了。
- 你关掉对话，第二天（新会话）再进来，他第一句话就是"上次你把我风筝踩泥里那事，我可还记着呢"——而且他真的开始准备报复（记仇值 +1）。
- 反过来，你要是帮阿铁修好了炉子，他嘴上别扭，但心里记着这份人情（恩情 +1，记仇值 −1），下次见面会给你留个好脸色。

**因果感**来自跨会话持久化：NPC 的态度不是存在模型上下文里，而是存在 PowerContext 的 Memory 里。Dify 只负责编排和表演，**记忆的真相在 PowerContext**。

## 2. 玩法与体验

| 环节 | 玩家做什么 | 系统发生什么 |
| --- | --- | --- |
| 进入 | 在 Dify 应用界面（Web App）里看到阿铁的开场白 | 工作流第一跳就用 `POST /v1/context/prepare` 读取该玩家的历史记忆 |
| 选择 | 在 `本轮行动` 里选「恶作剧 / 帮忙 / 结束冒险」，在 `详细描述` 里写细节 | LLM 节点根据历史 + 本轮动作生成阿铁的台词 |
| 结算 | 看到阿铁的回应 + 一行状态条（回合 / 记仇 / 恩情 / 态度） | 工作流把这一轮写进 PowerContext（事件记忆 + 状态记忆两条） |
| 收尾 | 选「结束冒险」 | 阿铁根据当前态度给出结局（报复 / 报恩 / 和解） |

### 输入设计

`开始` 节点有 3 个输入：

- `玩家ID`（text-input，默认 `player-1`）——决定用哪个存档。**换成别的 ID 就是另一个 NPC 记忆，互不干扰**。
- `本轮行动`（select：恶作剧 / 帮忙 / 结束冒险）。
- `详细描述`（paragraph）——玩家具体做了什么，会被写进记忆原文。

这样既支持"点按钮式"玩法，也支持自由发挥（描述里可以写任何细节）。

## 3. 状态机

```
                   恶作剧                     帮忙
        ┌────────────────────────┬────────────────────────┐
        │  记仇 +1               │  恩情 +1              │
        │  恩情 不变              │  记仇 −1              │
        └───────────┬────────────┴────────────┬───────────┘
                    ▼                         ▼
   ┌────────────────────────────────────────────────────┐
   │  态度判定（记仇值 grudge，区间 −5 ~ +5）             │
   │                                                    │
   │   grudge ≥ 3   → 死敌   （威胁、报复计划）          │
   │   grudge = 2   → 记恨                              │
   │   grudge = 1   → 记恨                              │
   │   grudge = 0   → 中立                              │
   │   grudge = −1  → 亲近   （别扭地道谢）             │
   │   grudge = −2  → 亲近                              │
   │   grudge ≤ −3  → 死忠   （留门、舍不得）            │
   └────────────────────────────┬───────────────────────┘
                                ▼
                     选择「结束冒险」→ 结局
                     死敌   → 「这辈子别再让我看见你。」
                     亲近/死忠 → 「……下回再来，提前说一声。」
                     其他   → 「走吧。」
```

### 三个结局

| 结局 | 触发条件 | 阿铁的反应 |
| --- | --- | --- |
| 报复 | 记仇值 ≥ 3（死敌） | 把锤子往铁砧上一摔，宣布不再见你 |
| 报恩 | 记仇值 ≤ −1（亲近/死忠） | 难得笑一下，让你下回提前打招呼 |
| 和解 | 其余情况（中立/记恨） | 背过身去敲他的铁，说"走吧" |

## 4. 记忆策略

### 4.1 存什么

每回合在 PowerContext 里写**两条**记忆（`kind` 是自由字符串，用来区分用途）：

| kind | 内容示例 | 作用 |
| --- | --- | --- |
| `prank_grudge` | `第1回合，玩家对阿铁使坏：把风筝踩进泥里。阿铁记下了这笔账。` | 事件：一次恶作剧 |
| `help_favor` | `第2回合，玩家帮了阿铁：修好了炉子。阿铁记着这份人情。` | 事件：一次帮忙 |
| `encounter` | `第3回合，玩家与阿铁：结束冒险。` | 事件：其他互动 |
| `npc_state` | `第2回合后状态：记仇=0，恩情=1，态度=中立。` | 状态快照：数值 + 态度 |

### 4.2 怎么读

新会话开始时，工作流并行发两个请求：

1. `POST /v1/context/prepare`（query = `玩家对阿铁做过什么，最近发生了什么`）
   返回带信任边界的 PreparedContext（`trust: untrusted_history`），作为**叙事历史**喂给 LLM。
   （这条 query 是实测挑出来的：它能同时召回"恶作剧"和"帮忙"两类事件；换成"我上次做了什么"这类问句反而只召回一条。`scripts/export_memory.sh` 用的也是同一条 query，所以导出的召回结果就是会话 B 当时真正拿到的那份。）
2. `POST /v1/memory/entries/list`（include_inactive=false）
   列出该存档的全部有效条目。Code 节点从中解析出：

   - `turn`：所有 `npc_state` 里回合号的最大值（+1 即本轮回合数）
   - `grudge` / `favor`：回合号最大的那条 `npc_state` 里的数值
   - `attitude`：由 `grudge` 映射出的态度
   - `history`：最近 6 条事件记忆的原文
   - `has_history`：有没有旧事（决定走"有旧账"还是"初次见面"分支）

> 为什么状态走 `entries/list` 而不是 `prepare`？`prepare` 是**按语义相关性**召回的，状态条目未必排在前面；状态必须**确定性地**读到，所以直接列全部条目再解析。

### 4.3 幂等与重置

- **存档隔离**：每个玩家一个 scope，`POST /v1/scopes` 的 `idempotency_key = dify-npc-<玩家ID>`，重复调用返回同一个 scope（`scope_id` 由服务端生成，形如 `scp_xxx`）。
- **软重置**：`scripts/reset.sh` 把当前存档里所有 active 条目 `retire` 掉，再写一条初始状态。服务不中断，适合反复验证。
  - 注意：每 retire 一条，Memory Artifact 的 revision 会 +1，所以必须**每次都重新 list 一遍**再 retire，否则会撞 `409 revision_conflict`。
- **硬重置**：`scripts/reset.sh --hard` 直接删 SQLite 库文件（需要重启服务）。

### 4.4 为什么用 PowerContext 而不是 Dify 的会话变量

| | Dify 会话变量 | PowerContext |
| --- | --- | --- |
| 生命周期 | 只在一次会话内 | 跨会话、跨进程、跨重启 |
| 题目契合度 | 只能证明"同一窗口记得" | 证明"换个窗口也记得" |
| 可审计 | 只能看运行日志 | 有 entry_id / entry_version_id / 时间戳，可导出 |

题面要求的是"**新会话中如何回应之前的互动**"，所以记忆必须落在会话之外。

## 5. 工作流编排（Dify 承担的核心逻辑）

14 个节点，全部在 Dify 里：

```
开始
 └─▶ [HTTP] 取得存档 scope        POST /v1/scopes
      └─▶ [Code] 解析 scope_id
           ├─▶ [HTTP] 读取跨会话记忆   POST /v1/context/prepare
           └─▶ [HTTP] 列出记忆条目     POST /v1/memory/entries/list
                └─▶ [Code] 还原 NPC 状态（turn / grudge / favor / 态度 / 历史）
                     └─▶ [If-Else] 有旧账吗？
                          ├─ true  ─▶ [LLM] 阿铁反应（有旧账）──┐
                          └─ false ─▶ [LLM] 阿铁反应（初次见面）─┤
                                                             ▼
                                              [Variable-Aggregator] 合并模型输出
                                                             ▼
                                              [Code] 合并状态（算新数值 + 要写入的记忆）
                                                             ▼
                                              [HTTP] 写入本轮记忆  POST /v1/memory/remember
                                                             ▼
                                              [HTTP] 写入 NPC 状态  POST /v1/memory/remember
                                                             ▼
                                                   回应（台词 + 状态条）
```

对应题面要求的五件事：

| 题面要求 | 在哪里实现 |
| --- | --- |
| 输入处理 | `开始` 节点的三个输入（玩家 ID / 行动 / 细节） |
| 模型调用 | 两个 LLM 节点（角色扮演与台词生成） |
| 条件判断 | `If-Else` 节点：有旧账 → 主动提起；无旧账 → 初次见面 |
| HTTP 调用 | 5 个 HTTP Request 节点，全部指向 PowerContext |
| 结果输出 | `回应`（Answer）节点，输出台词 + 状态条 |

> 编排的可视化：`evidence/workflow-graph.svg`（由 `scripts/render_workflow_svg.py` 直接读 `dsl/grudge-npc-chatflow.yml` 渲染，图 = 导出的 DSL，不是手绘）。
> 每次运行每个节点的实际输入输出：`evidence/dify-node-runs.md`。

### 两条分支为什么必须走两个 LLM 节点

Dify 的分支是**互斥**的：走 true 分支时 false 分支的节点不会执行，直接引用它的输出会报错。
所以两个分支各写一个 LLM 节点，再用 `variable-aggregator` 把两条互斥分支的输出合并成一个变量，
后面的 Code 节点只认这个合并后的值。

### 数值变化为什么放在 Code 节点而不是让模型算

状态机是规则，不是创作。让 LLM 去输出 `grudge_delta` 会带来"模型忘了加一"这类不确定性，所以：

- **模型只负责说话**（`say` + `detail`）；
- **数值由 Code 节点按确定性规则计算**（恶作剧 → 记仇 +1；帮忙 → 恩情 +1、记仇 −1；结束冒险 → 不变）；
- **模型看到的 grudge/favor 是从 PowerContext 读出来的真值**，所以台词里的态度和状态条永远一致。

## 6. 已知限制

1. `POST /v1/memory/entries/list` 返回该存档的全部条目，条目很多时响应会变大；本作为小样本游戏（每次验证十几条以内），未做分页。
2. PowerContext 最小服务用**全文检索**（`mode: fts`），没有配置向量模型时 `prepare` 按词面相关性召回。历史描述用词差异大时，可能召回不全（例如玩家说"踩了风筝"，记忆里写的是"踩进泥里"）。要更强的召回可以给 PowerContext 配置向量检索。
3. NPC 状态只有一个轴（记仇值）与一个辅助轴（恩情值），没有做多属性（比如好感度、信任度、体力值）。
4. Dify 的 Chatflow 本身不保证"新会话"这一概念对普通用户显而易见，README 里特别强调了用"新建对话"来验证跨会话记忆。
