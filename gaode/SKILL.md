# 周边去哪儿：基于高德的地点推荐助手

## 1. 用途与适用场景

**用途**：把一句自然语言需求变成一份**地点真实、步行距离与耗时可核对**的周边推荐清单。

典型输入：
> “我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。”

输出：最多 3 个步行可达的真实地点，每个带名称、地址、预计步行距离与时间、一句有数据依据的推荐理由，并说明查询范围与未核实项。

**适用场景**
- 泛需求：“附近有什么值得去的地方？”
- 定点定类：“地铁站 B 口出来，步行 10 分钟内有哪些咖啡馆 / 餐厅 / 公园 / 书店 / 药店？”
- 带约束：“找 3 家步行能到的健身房，优先近一点。”
- 换词兜底：“附近适合遛娃、能歇脚的地方有哪些？”

**不适用**：跨城与多日行程；驾车/骑行/公交路线；需要实时排队、营业、安静程度等实时属性判断。

## 2. 工具路由（先确认，再调用）

评测环境已配置高德 MCP Server。**开始前先读取当前可用工具清单（tools/list）确认实际工具名与参数**，按下表做语义匹配。表中的别名指向同一能力：**工具名与下表不完全一致时，按语义选工具，不要因为名字不同就换数据源、跳过调用或自行编造结果**。

| 能力 | 首选工具 | 常见别名 | 关键参数 |
| --- | --- | --- | --- |
| 地名/地址 → 坐标（地理编码） | `maps_geo` | `maps_geocode`, `geo` | `address`, `city?` |
| 坐标 → 行政区划（逆地理编码） | `maps_regeocode` | `regeocode` | `location` = `"经度,纬度"` |
| 按坐标 + 关键词找附近 POI | `maps_around_search` | `maps_around`, `around_search` | `location`, `keywords`, `radius`（米） |
| 按关键词 + 城市找 POI | `maps_text_search` | `maps_place`, `maps_poi_search` | `keywords`, `city?`, `offset?` |
| POI 详情（补坐标/类型/地址） | `maps_search_detail` | `maps_poi_detail`, `maps_detail` | `id`（高德 POI ID） |
| 步行路径规划（距离 + 耗时） | `maps_direction_walking_by_coordinates` | `maps_direction_walking`, `maps_walking` | `origin`, `destination`（均为 `"经度,纬度"`） |
| 步行路径规划（按地址） | `maps_direction_walking_by_address` | — | `origin_address`, `destination_address`, `origin_city?`, `destination_city?` |
| 两点距离（仅可选粗筛） | `maps_distance` | — | `origins`, `destination`, `type=1`（步行） |
| 城市天气（可选） | `maps_weather` | — | `city` |

**返回字段形状（按实际返回取值，字段名以本次调用为准）**
- `maps_around_search` 返回的 POI 常只含 `id` / `name` / `address` / `typecode`，**往往不带坐标**。因此：对筛下的候选**逐个调用 `maps_search_detail(id)`** 取得 `location`（`"经度,纬度"`）、`type`（中文类型串，如 `"餐饮服务;咖啡厅;休闲餐饮"`）、`business_area`、`rating`、`opentime` 等，再进入路线查询。若该次周边搜索已返回 `location` 与 `type`，可跳过详情调用。
- `maps_text_search` 返回的 POI 通常直接带 `location` 与 `type`。
- 步行路径规划返回路径数组（常见为 `route.paths[]`，也可能是 `data.paths[]` 或顶层 `paths[]`），每个 path 含 `distance`（**米**）与 `duration`（**秒**），`steps[]` 含分步 `instruction` / `road` / `distance` / `duration`。
  - 展示换算：`分钟 = duration / 60`（展示时向上取整）；距离 < 1000 米按米展示，≥ 1000 米按公里保留一位小数。
  - **只使用工具真实返回的距离/耗时字段**，不要用字段名的直觉猜测数值。

## 3. 需求解析：先建“需求卡”

从用户输入中抽取下列要素；用户未指定时使用默认值，并在最终回答中说明所用默认值。

| 要素 | 抽取方式 | 缺省处理 |
| --- | --- | --- |
| 起点坐标 | 评测会给出明确坐标；未给出则用 `maps_geo` / `maps_regeocode` 解析起点名 | 解析不到唯一结果时先确认，不擅自挑一个 |
| 起点名称 | 用户给的地铁站/地址/POI 名 | 用逆地理编码或 POI 结果补全 |
| 城市 | 用户提到的城市名 | 取起点的 `city` / `adcode` |
| 地点类型 | 口语 → 高德关键词：咖啡馆→`咖啡`；吃饭→`餐厅`；吃的→`餐厅`+`快餐`+`小吃`；公园→`公园`；药店→`药店`；书店→`书店`；超市→`超市`+`便利店`；运动→`健身房`+`运动`；景点→`景点`+`博物馆` | “值得去的地方”→按 2–4 个类目分别搜（咖啡/餐厅、公园/景点、休闲娱乐/书店），合并去重 |
| 步行时间上限 | “步行不超过 15 分钟” | 15 分钟，并在回答里注明这是默认值 |
| 推荐数量 | “推荐最多 3 家” | 3（硬上限 3） |
| 排序偏好 | “优先近一点” | 一律按步行耗时升序（近→远），同耗时按步行距离、再按名称 |
| 其他偏好 | 安静、排队、营业、是否可带宠物、是否需要预约 | **无数据支撑时标注“未核实”，不得推断或编造** |

关键词要点：高德按中文关键词匹配，**用类目词而不是完整店名**。首轮无结果时换同义词或上位词再搜一轮（如 `咖啡` → `咖啡厅` → `咖啡店`；`吃的` → `餐厅` → `中餐厅`）。品牌名搜索交给 `maps_text_search`。

## 4. 执行流程（六步）

**Step 1｜确认起点**
- 优先使用用户给出的坐标与起点名；坐标格式为高德 GCJ-02 的 `"经度,纬度"`（**经度在前**），不得与 WGS84 混用、不得颠倒经纬度。
- 起点是地铁站时，**直接使用给定坐标**，不要替换成“某出口”或附近地标的坐标。
- 若需解析起点，用 `maps_geo(address, city)` 或 `maps_regeocode(location)`；同名地点用城市/区/地址消歧，仍歧义则列出候选请用户确认。

**Step 2｜召回候选（周边搜索）**
- `maps_around_search(location=起点坐标, keywords=类型关键词, radius=R)`。
- 半径换算：`R ≈ ceil(步行上限分钟 × 80 m/min × 1.3)`，夹到 `[300, 50000]`。例：15 分钟 → 1200 m × 1.3 ≈ 1560 m，取 1500–2000 m；30 分钟 → 取 3000–3500 m。80 m/min 约合 4.8 km/h 常规步速。
- **radius 只是召回范围，不是“可达”的结论。** 可达性一律由 Step 4 的步行路径规划判定。
- 单页返回有限条数；同一类目最多翻到第 2 页，避免批量刷点与高频调用。
- 泛需求场景按 2–4 个类目各搜一次，合并结果后按 POI `id` 去重（同名不同 `id` 视为不同门店，可保留但要标明是不同门店）。

**Step 3｜补齐候选信息**
- 先按 `name`/`id` 粗筛到不超过 8 个候选，再逐个调用 `maps_search_detail(id)`。
- 用返回的 `type`（中文类型串）确认类型符合需求；`typecode` 仅作辅助，**不确定时不要据此硬删候选**。
- `address` 为空时，用 `business_area` + 区/市补成“××区××商圈（高德 POI 地址字段为空）”，并标注该字段缺失。

**Step 4｜步行路线查询（耗时与距离的唯一来源）**
- 对每个候选调用步行路径规划，**优先坐标版**：起点 = 用户给的起点坐标，终点 = 候选 POI 的 `location`。
- 各候选彼此独立，可一次并发发出多个路线请求；`origin` 保持同一个起点坐标，不要用候选附近的锚点坐标替代。
- **步行距离与预计耗时只能取路线查询返回的 `distance` / `duration`**；禁止用直线距离换算、禁止用周边搜索半径反推、禁止用“常识”估步速。
- 某候选路线查询报错或超时 → 该候选标记“路线查询失败”，不入选、不编造数据；可换地址版工具重试一次，仍失败则按未核实处理。

**Step 5｜筛选与排序**
- **硬过滤**：`步行耗时 ≤ 用户上限`。超时地点**不得**出现在“符合条件”的推荐列表中。若用户想看近一点的备选，另起一节“超出步行上限（未计入推荐）”列出并标明真实耗时。
- **数量**：最多 3 个（或用户指定数，上限 3）。不足就少给并说明原因，不为凑数放宽硬性条件。
- **排序**：按步行耗时升序，距离同序，同耗时按名称。“优先近一点”即此顺序，**推荐顺序必须与路线数据一致**，不要按周边搜索返回顺序排列。
- 硬性条件（类型、步行上限、数量）优先于任何偏好；偏好只影响排序与措辞。

**Step 6｜生成回答**
按第 5 节模板输出，最后自查第 8 节的清单。

## 5. 回答格式

用**表格**呈现（列表亦可，但每条必须包含同样字段）。每个地点必须有：名称、地址、预计步行距离、预计步行时间、一句推荐理由。

```
以「<起点名称>（<坐标>）」为起点，找到 <N> 个步行 <X> 分钟内可达的「<类型>」（高德 POI 搜索 + 高德步行路径规划，查询时间 <YYYY-MM-DD HH:MM>）：

| # | 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | <名称> | <地址> | <米/公里> | 约 <N> 分钟 | <有数据依据的一句话> |
| 2 | <名称> | <地址> | <米/公里> | 约 <N> 分钟 | <有数据依据的一句话> |
| 3 | <名称> | <地址> | <米/公里> | 约 <N> 分钟 | <有数据依据的一句话> |

说明：
- 表中步行距离与耗时均来自高德步行路径规划的返回结果（米/秒换算为分钟），不是直线距离估算。
- 营业时间、排队情况、安静程度、人流量、是否需要预约等本次未核实，如需要请出行前确认。
- 数据来源：高德地图 POI 搜索与步行路径规划；查询时间 <时间戳>。
```

**推荐理由可用的依据（只能从下列真实返回字段中组合）**
- 步行耗时/距离在本次候选中的相对位置：“最近的一个”“耗时第二短”
- 高德 POI 返回的类型：`type` 字段（如“餐饮服务;咖啡厅;休闲餐饮”）
- 地址与商圈：`address`、`business_area`
- 高德 POI 详情中的 `rating`、`cost`、`opentime`（须写明“高德 POI 字段”，并把营业状态表述为“查询时刻的平台快照”）

**推荐理由禁止出现的内容**（无数据支撑，一律不写）
“安静/人少/氛围好/排队短/现在一定营业/本地人都去/性价比最高/味道好/环境好/适合拍照/不用排队”等。若用户主动问到这类信息，回答“该属性不在高德地点与步行路线数据范围内，未核实”。

**其他格式约定**
- 距离单位：< 1000 m 用“米”，≥ 1000 m 用“公里（一位小数）”；耗时统一用“约 N 分钟”。
- 不输出坐标以外的原始 JSON、不输出 API Key、不复述工具报错堆栈。

## 6. 结果不足、信息缺失与调用失败

| 情况 | 正确做法 |
| --- | --- |
| 周边搜索 0 结果 | 换同义词/上位词重搜一次；再把 radius 放大到上限的约 2 倍重搜一次；仍无则如实说明“以起点为中心 <R> 米范围内未检索到「<关键词>」相关 POI”，并建议放宽关键词、换起点出口或延长步行时间。**不得编造店名** |
| 有候选但全部超时 | 如实说明“检索到 <N> 个候选，但没有一个在 <X> 分钟内步行可达（最近的一个约 <Y> 分钟）”，可把最近的一个单列为“超出步行上限（未计入推荐）” |
| 结果少于要求数量 | 说明“符合步行 ≤ <X> 分钟条件的只有 <N> 个，少于请求的 <M> 个”，并给出原因（检索半径/关键词/该城市该类型确实稀少） |
| 个别路线查询失败 | 该候选标注“步行路线查询失败，未计入推荐”，用其余成功候选作答；一个都不能成功时说明失败情况，不给出距离时间 |
| 高德工具整体不可用 | 明确写“高德地点/路线服务本次调用失败（<错误摘要>）”，**不输出任何猜测的地点、距离、时间**；建议重试或稍后再试 |
| 起点无法解析 / 同名歧义 | 列出解析到的候选（名称 + 地址）请用户确认，不要擅自选一个继续推荐 |
| 起点坐标缺失且无法解析 | 说明缺少起点信息并请求补充，不做推测 |

诚实性优先于数量：**宁可少推荐并说明原因，也不要为凑满 3 个而放宽步行上限、类型或编造数据。** 无结果的用例按“是否正确处理”评分，推荐数为 0 本身不扣分。

## 7. 数据真实性红线

1. 名称、地址、坐标、步行距离、步行耗时**只能**来自本次工具调用返回的字段；禁止凭常识或记忆补全店名，禁止用直线距离换算步行耗时。
2. **周边搜索的返回顺序不等于推荐排序**；排序必须由步行路线数据决定。
3. 不得引用本次调用中不存在的 POI，不得为“更丰富”的推荐引入未经查询的地点。
4. 超过步行时间上限的地点不得出现在符合条件的推荐列表中。
5. 数量不足时如实说明，不擅自放宽硬性条件。
6. 不输出、不记录、不复述 API Key 等凭据。
7. 只做只读检索与规划：不代替用户导航、叫车、预约、下单。

## 8. 交付前自检清单

- [ ] 每个推荐地点都能在本次工具返回中找到对应的 POI（名称 + id）
- [ ] 每个距离/耗时都有对应的步行路径规划返回作为出处
- [ ] 所有入选地点的步行耗时 ≤ 用户上限
- [ ] 推荐数量 ≤ 用户要求且 ≤ 3；不足时已说明原因
- [ ] 推荐顺序与步行耗时数据一致（近 → 远）
- [ ] 地点类型与用户需求一致（依据 `type` 字段）
- [ ] 未核实属性已标注“未核实”，未出现无依据的描述
- [ ] 无结果 / 查询失败的情况已如实说明并给出放宽建议
- [ ] 回答未包含密钥、原始 JSON 或工具堆栈

## 9. 示例（格式演示，数值为示意，非真实查询结果）

> 用户：“我在杭州某地铁站，想找一家咖啡馆，步行不超过 15 分钟，推荐最多 3 家，优先近一点的。”

```
以「杭州××地铁站（120.16xxxx,30.27xxxx）」为起点，找到 2 个步行 15 分钟内可达的「咖啡馆」（高德 POI 搜索 + 高德步行路径规划，查询时间 2026-01-01 10:00）：

| # | 地点名称 | 地址 | 步行距离 | 预计步行时间 | 推荐理由 |
|---|---|---|---|---|---|
| 1 | ××咖啡（××路店） | 西湖区××路××号 | 320 米 | 约 5 分钟 | 高德 POI 类型为「餐饮服务;咖啡厅;休闲餐饮」，从起点步行 320 米约 5 分钟即达，是本次候选中最近的咖啡馆。 |
| 2 | ××咖啡（××广场店） | 西湖区××路××号××广场 | 780 米 | 约 11 分钟 | 同为高德「咖啡厅」类型，步行 780 米约 11 分钟，在 15 分钟上限内；商圈位于××广场。 |

说明：
- 表中步行距离与耗时均来自高德步行路径规划的返回结果（米/秒换算为分钟），不是直线距离估算。
- 营业时间、排队情况、安静程度、人流量等本次未核实，如有需要请出行前确认。
- 满足条件的咖啡馆只有 2 个，少于请求的 3 个：地铁站周边 1.5 公里内高德仅检索到这 2 家咖啡类 POI；可放宽到 2 公里或改搜「咖啡店」「茶饮」再试。
- 数据来源：高德地图 POI 搜索与步行路径规划；查询时间 2026-01-01 10:00。
```
