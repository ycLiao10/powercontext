# 集合与底层表的映射关系

seekdb SDK 采用集合这一层抽象，底层对应一张真实的物理表，表名由集合名和集合 id 拼接而成，中间用下划线分隔。比如集合名是知识库加模型短名，集合 id 是 42，那么实际表名就是这两者用下划线连起来的结果。

这个命名方式带来一个实际影响：集合名里带短横线是允许的，但表名会被拼进 SQL 语句，在需要反引号包裹的场景下要特别小心。我们的调试接口里直接用模板串拼表名，排查问题时最好先把拼出来的表名手动执行一遍建表语句查询，确认结构和自己预期的一致。

集合 id 是服务端分配的，同名集合重建后会拿到新的 id，旧表不会自动删除。我们测试时反复删除重建同一个集合，几次之后数据库里堆了好几张同名前缀的孤儿表，每张都带着几 MB 的向量数据。后来我们加了一条清理流程：删除集合之后显式扫一遍表前缀，把同名不同 id 的表一并删掉。

因为表名里有随机 id，代码里不能把表名硬编码。我们把表名推导集中在一个函数里，其他地方一律通过这个函数拿，避免出现某处忘了加下划线这类低级错误。这个小重构花了一小时，但之后所有涉及表名的日志输出都能保证和库里真实存在的表对得上。

集合列表接口返回的每个集合描述里带着维度、距离度量和文档条数，这些信息非常适合直接渲染成状态面板，不用再单独查表统计。我们做前端的时候就是直接复用了这份返回，省掉了一轮往返，顺带把距离度量也显示出来，方便确认索引配置是否符合预期。

如果要手工清理历史数据，可以先按前缀把候选表列出来，确认条数不多再逐个删。直接写一条通配删除语句是不可取的，集合名和表名都可能带上前缀相同的其它内容，误删的代价远高于手工多花几分钟。
