# 存储引擎与表组织方式的选择

seekdb 建表时可以指定表组织方式，常见的选项是堆表和列存表两类。堆表按行组织，整行数据连续存放，读取单行时只需要一次物理读；列存表按列组织，同一列的值连续存放，做聚合和列过滤时扫描效率高得多，两者在我们的知识库场景里各有明显优势。

我们的知识库表既有宽文本，原始文档动辄上千字，又有窄数值，向量维度固定、元数据是 JSON。如果整张表都用列存，读取原文时会把其他列的空洞也一起拉过来，磁盘带宽被浪费；如果整张表都用堆表，按向量做过滤扫描时又缺乏列裁剪能力。

折中做法是把向量单独放进一张列存表，把原文和元数据放在堆表，两张表通过文档 id 关联。检索时先在向量表上跑近邻，再回到堆表取回正文。代价是多一次随机读，收益是两种访问模式都不吃亏，在几十万行量级上这个交换是划算的。

不过当前 SDK 生成的表结构是固定的，组织方式写死在建表语句里，正文和向量在同一张表。为了后续能演进，我们在自己的封装层保留了显式传入组织方式的入口，等哪天需要列存隔离时不用改上层调用逻辑，只改 schema 构造部分。

表属性里的分区键不要随手加。我们早期按时间分区，结果每个分区都要独立维护一份索引副本，十几万行数据时 HNSW 图的内存占用翻了好几倍，查询时还要跨分区做归并，整体反而更慢。

行存表的空间放大问题也要留意。正文列是可变长字符串，如果表上同时有行外的大字段存储配置，实际读取会把正文拆成多段寻址，延迟抖动明显。我们把正文控制在两三千字以内，一个段落一条记录，既避开大字段拆分，也不至于让全文索引的倒排链过长。

综合取舍下来，我们的结论是单表堆存储加适度分片。数据量在几十万条以内时，单表方案的运维成本远低于多表关联，而真正的性能瓶颈会先出现在向量索引上，而不是存储组织方式上。
