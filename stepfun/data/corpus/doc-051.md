# 浏览器侧的内存占用与垃圾回收抖动

端侧最容易被忽视的资源是内存。模型权重、计算图、推理会话，再加上语料的向量数组，全都堆在同一个浏览器的进程里。

向量是最容易失控的部分。一千两百篇文档乘 512 维，如果每维都按双精度浮点存，一条向量就是 4KB，两千多条加起来接近 10MB，还要算上每个数组对象自身的开销。我们把中间结果改成 Float32Array，同样的数据只占 2KB 一条。

第二个内存黑洞是中间张量。每次前向计算都会产生若干临时张量，如果它们在等待期间还被引用着，垃圾回收器就没法回收，内存曲线会呈阶梯状往上涨，直到某一刻集中回收造成一次明显的卡顿。

我们的做法是批处理结束后立刻把批次结果转换成普通数组并丢掉张量引用，不把张量保存在任何长期变量里。转换本身有开销，但换来了可预测的内存曲线。

另一个技巧是复用输出缓冲区。把向量结果写进一个预分配的 Float32Array 而不是每次都新建，循环里就不会产生大量短命对象。

排查内存问题可以用性能面板的堆快照，对比导入前后的差异。如果导入完成之后堆里还留着大量文本和中间对象，说明引用链没有断干净。

内存峰值和设备的实际可用内存有关。我们把批大小限制在 8，一部分原因就是防止在低配机器上一次性申请太多连续内存导致分配失败。
