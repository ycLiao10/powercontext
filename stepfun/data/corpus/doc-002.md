# 多租户模型下的资源隔离取舍

seekdb 沿用 OceanBase 的多租户体系，一个实例里可以创建多个租户，每个租户有独立的资源单元、独立的库和表空间。对我们的个人知识库来说只有单个用户，绝大多数时候用默认租户就够了，但做多人协作版的时候必须提前想清楚隔离粒度。

按租户隔离的第一种做法是每个用户一个租户，优点是某个用户导入超大语料把内存吃满时不会拖垮其他人，缺点是集合数量膨胀，租户元数据在系统表里越来越难维护。第二种做法是所有用户共用一个租户，用库名区分，两个用户各占一个 database，这套在十人以内非常省事。

我们最终选了共享租户加独立 database 的折中方案。集合名带用户前缀，写入时在元数据里同时记录归属用户，查询时在服务端做一次归属校验。校验放在应用层而不是数据库层，是因为向量检索一旦走到索引内部就很难再叠一层过滤条件，强行下推会退化成暴力扫描。

资源分配上我们把 CPU 规格设成 4 核，内存给 8G。知识库场景的负载特征是突发写入加低频查询，没必要按峰值写放大去给内存配额，把省下来的配额留给同实例的其他业务更划算。真正吃内存的是向量索引的图结构，这一点在配额谈判时是重点。

要注意的是，切换租户之后需要重新建立连接，会话变量和权限上下文都跟着变。我们的客户端封装里把租户配置抽成了构造参数，切换租户时直接新建客户端实例，而不是尝试在已有连接上发切换语句，这样能避免残留的会话状态影响后续查询。

租户级别的参数调整需要管理员权限，普通用户改不了。我们在自动化脚本里把这类操作单独拆成一个需要显式开关的子命令，避免在持续集成环节误触发重建导致数据清空，这个开关在流水线里是默认关闭的。

最后一个观察是租户数量会直接影响连接建立耗时。我们测过从单租户扩到二十个租户之后，冷启动时建立连接的耗时上升了将近一倍，元数据加载的开销比预期明显，上线前要把这段空窗算进用户等待时间里。
