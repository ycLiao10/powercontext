# 用 Web Worker 卸载推理的取舍

浏览器的主线程同时负责渲染和交互，推理如果跑在上面，长时间会阻塞输入响应。我们的前端在每批之间会让出主线程，界面不会完全卡死，但响应性依然会下降。

把推理放进 Worker 是彻底的解法。Worker 有自己的线程池，消息通过结构化克隆传递。主线程只负责发文本、收向量，其余时间完全空闲。

代价是数据要来回搬。文本进 Worker 是一份拷贝，向量出来又是一次拷贝。我们的向量是 512 维的普通数组，结构化克隆之后在新线程里是另一份内存，数据量大时这个拷贝并不便宜。

我们试过用可转移对象把 ArrayBuffer 直接转移过去，零拷贝，但转移之后原线程就失去了这个 buffer 的所有权，需要重新分配才能再传下一次。对一次性的大批量导入划算，对反复的单条查询就不合适。

我们最终没有上 Worker，原因是规模。个人知识库的语料通常在几百篇，一次导入的推理时间在十几秒量级，分批让出主线程已经能维持可接受的响应性。为此引入一套双线程通信框架，调试成本明显高于收益。

判断要不要上 Worker 有个简单的标准：如果一次批量推理超过两秒并且用户在这期间需要继续操作，那就值得。我们现在是前者不满足、后者成立，所以先不动。

但有一个例外是模型加载。加载阶段没有返回值要传，纯粹是耗时，把它放到 Worker 里收益明显而且没有拷贝成本。
