# 排查时该看哪些系统视图

OceanBase 提供了一批系统视图用于观测内部状态，最常用的是 GV$OB_UNITS、GV$OB_TENANT_RESOURCE_USAGE 和 GV$SESSION 这几类。前两者给出资源分配与实际占用的对照，第三个能看到当前所有会话在执行什么。

资源占用的对照最有诊断价值。规格给的是上限，实际用量能看出内存到底被谁吃掉了。我们定位过一次租户内存莫名变高的问题，发现内存占比远超预期，最后查到是执行计划缓存里的语句没有复用，每个不同形状的查询都在缓存一份。

GV$SESSION 里最常用的是 svr_ip、svr_port、sql_id 和 elapsed 这些字段。sql_id 是对归一化后的 SQL 取的哈希，同一模板的慢查询会聚到同一个 id 上，按 sql_id 聚合就能直接看出哪类语句拖慢了整个实例。

我们做故障排查的习惯是先用 sql_id 把慢查询聚类，再回到应用日志里找对应的时间点。这个顺序能省掉大量逐条翻日志的时间，因为参数不同的同模板查询在日志里长得几乎一样，只有 sql_id 能把它们区分开。

慢日志是另一个廉价而有用的来源。它按语句耗时排序，抓取时不需要额外的采样配置，对偶发的长尾查询特别有效。我们把慢日志的阈值设成 200 毫秒，比大多数正常查询高出一个数量级，因此记录量不大，但每次打开都有内容。

有一张表值得单独提一下，就是记录最近错误码的视图。OceanBase 的很多报错只有数字码没有文字说明，光看码很难判断是锁冲突还是资源不足。我们把常见错误码整理成一张对照表放在排查手册里，新同事照着查基本能覆盖八成的问题。

提醒一句，系统视图本身也有开销，在高并发下频繁查询反而会加重负担。我们只在排查时查，日常健康检查只保留两三个最轻量的指标。
