# 带过滤条件的向量检索

实际业务里的检索很少是纯近邻查询，通常还要叠加一层条件，比如只看某个来源的文档、只看某个时间之后的内容，或者是某类标签。这类带条件的向量检索，实现上有先过滤和后过滤两条路。

先过滤是把条件翻译成一次范围扫描，把命中的候选集取出之后再建索引做近邻搜索。它的问题是候选集可能很大，条件不收敛时退化成全表扫描，延迟非常不可控。我们的知识库总量不大，但过滤后只剩几十条的时候，先过滤反而最划算。

后过滤是先把向量全部检索出来，取回文档之后在应用层或者 SQL 里判断条件。它的语义直观，但有一个隐蔽的坑：如果符合条件的文档排在召回窗口之外，查询就会漏掉它们。窗口取 100 而符合条件的只有 3 条排在第 120 位，那么结果就是空的。

混合检索里这个问题更突出。全文和向量两路各自取候选，再融合排序，条件如果只作用在其中一路，另一路的候选会把不满足条件的文档带进融合池，最后再过滤就已经晚了。

我们的做法是把过滤条件尽量下推成 SQL 里的条件，同时保证召回窗口足够大。另外在接口层明确约定：过滤条件是收窄结果的，不是一个精确的权限系统。真正的数据隔离必须靠分库分租户来做，不能指望检索时的过滤条件。

这一点在多人协作场景里尤其重要。我们早期把用户标识当成一个过滤字段直接下推，结果一旦有人构造出没有过滤条件的查询，就绕过了隔离。后来我们把隔离挪到租户或者 database 层面，过滤字段只用于排序和粗筛。
