# 向量列的类型与维度约束

OceanBase 的向量列用 VECTOR 类型声明，语法上要带上维度，例如 512 维的写法。维度在建表时就固定下来，之后任何一行数据的向量长度都必须严格等于这个值，多一个少一个都会在写入时报错。

我们在建集合时把维度直接取自模型元数据，中文小模型是 512 维，轻量多语模型是 384 维。因为不同模型本来就要落在不同的集合里，集合名按模型短名区分，这样切换模型时连表都不用换，服务端的集合管理逻辑完全不用改。

维度还有一个容易忽略的约束：它直接决定了单个向量占用的字节数。512 维的 float32 是 2048 字节，一万篇文档就是 20MB 左右的裸向量数据。换成 INT8 量化后每维只要 1 字节，体积直接降到四分之一，这是我们做量化收益测算的基线数字。

写入路径上我们把维度校验放在了浏览器端而不是服务端。浏览器在批量向量化时已经知道每条向量的实际长度，一旦发现长度和集合声明不一致就直接抛错并中止这批导入，而不是让服务端逐行报错再回滚，后者在大批量场景下会产生大量无谓的往返。

维度不匹配这个错误在客户端表现得很隐蔽：HTTP 状态码是 200，真正的错误信息藏在返回体里。我们的接口封装统一把写入条数和总数两个字段一起检查，只要写入条数和预期对不上就判定为失败，并把这批数据退回重算。

维度上限也要留意。OceanBase 对单列向量维度有上限规定，超出之后建表会直接被拒。我们如果将来换更大的模型，务必要先确认上限，不要等数据都算好了再发现存不下，那意味着前面所有的向量化工作全部作废。

还有一个容易忽略的点是维度和量化格式的绑定关系。量化后的向量每一维占用的字节数变了，但维度本身不变，所以量化前后的集合结构完全一致，我们不需要为 INT8 版本单独建一套表，切换精度方案时只换写入的向量数据。
