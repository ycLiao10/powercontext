# schema 演进与集合结构迁移

表结构一旦建好就不该随便改，但实际需求会变，问题在于怎么改才不会把已有数据搞坏。

最容易踩的是改向量列的维度。维度是建表时就固定的，改不了，只能重建集合。我们把这一点当成硬约束：换模型就换集合，而不是改表。这也是集合名里带模型标识的原因。

可以原地改的是非向量列。我们加过一个来源文件名列，加的时候不需要重建集合，几秒钟就完成了。但如果这一列需要参与过滤或者需要建索引，就不只是加列那么简单了。

改索引参数是最贵的一类变更。距离度量、图的 m 值、构建参数一旦和索引里的数据不一致，结果就是错的。建索引时的参数是写进表定义的，改它意味着整表重建。

全文索引的分词器改动也属于重建类。切词结果已经固化在索引里，换分词器必须重新灌一遍数据。我们试过只重建全文索引而保留向量数据，后来发现没有可靠的接口能只重建一部分，索性改成整套重来。

我们把 schema 变更分成三档：加普通列是原地改，删列是原地改但要确认没有依赖它的索引，改索引参数或换维度是整套重建。这个分档写在变更流程里，提交之前先对号入座。

迁移的流程是标准的：建新集合、灌数据、刷新索引、对比验证、切换流量、切掉旧集合。最后一步经常被忘记，旧集合留着会一直占内存和磁盘。

对比验证这一步我们用的是同一套评测脚本跑新旧两个集合，比较 Recall@K 和延迟。迁移的收益必须能被数据证明，否则不值得做。

另外还有一个容易忽略的点：集合名一旦确定就不要改。名字里编码了模型、精度和用途，它同时是切换模型时的路由键，改名等于让所有历史引用失效。
