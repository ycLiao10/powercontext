# 来源撤回、证据选择与上下文拼装

检索到结果之后还有一步：决定哪些证据可以进入最终的上下文，以及当原始文档被删除或修改时怎么办。

来源撤回的核心问题是派生数据的失效。我们把向量和倒排索引都当成可重建的派生物，源文档才是事实来源。删除一篇源文档时，不能只删向量，得让它的全文索引条目也失效，否则关键词还能搜到一篇已经不存在的文档。

我们的处理方式是把文档的撤回状态放进元数据，同时从库里真正删除对应的向量记录，两件事一起做。少做一件就会留下幽灵命中。

有一个我们踩过的坑：只改状态不删向量，检索照样能命中，用户点进去看到的是"该文档已失效"。这比搜不到更让人困惑，因为用户会以为文档还在，只是内容变了。

证据选择的原则是宁可少给也不要给错。进入上下文的每一段都要同时满足两个条件：标注上相关，并且自身的信息量足够。一段话如果只是"本文讨论了向量检索"，它对回答问题没有贡献，哪怕它确实很相关。

相邻的段落可以合并成一块证据。检索经常返回同一篇文档的连续两三段，它们其实是一个完整的论述，分开呈现会让读者反复阅读重叠的内容。

上下文拼装还有长度预算。预算按 token 算而不是按字符算，因为不同模型的 tokenize 粒度不同。超预算时的取舍顺序是：先砍相关性最低的，再砍重复的，最后才砍证据内部的句子。

拼装顺序也有讲究。我们按相关性降序排列，但把彼此有依赖的段落放在一起，因为顺序被打乱之后，后面的段落可能读不懂。

最后，每个进入上下文的证据都要带上来源标识。这不只是为了可解释性，也是为了让下游能够在源文档被撤回之后，把相关结论一并作废。
