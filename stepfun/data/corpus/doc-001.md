# seekdb 单机部署与连接参数

我们把 seekdb 1.4.0 跑在一台 8 核 16G 的 Linux 开发机上，用官方镜像启动，再用配套的诊断容器做排查。镜像默认以开发模式拉起 observer，日志输出比较啰嗦，但正适合调试期把选主、租户创建这些关键状态都看清楚。

容器起来后默认监听 2881，这个端口同时承载 MySQL 协议接入和租户元数据管理，不要和业务应用共用同一个端口映射，否则抓包时会把元数据流量和真实查询流量混在一起。诊断容器我们单独映射到另一个端口，只在需要时连上去，避免日常开发时误操作影响主实例。

连接串统一写成 `root@127.0.0.1:2881/test`。密码为空时也要显式传空字符串而不是省略字段，SDK 在某些版本会把 `password: undefined` 理解成使用默认空密码，但在带租户的部署里会退回到系统租户，表现像是连上了却查不到表，排查起来非常绕。

初始化阶段必须等 observer 完成选主，日志里出现服务正常运行的标志之后才能发建表请求。我们踩过的坑是自动化脚本跑得太快，第一次建集合直接返回内存类错误，重试两次才成功。后来改成在健康检查里轮询版本号查询，拿到非空版本号才继续往下走，这个改动让部署脚本变成了一次性成功。

内存配置是最容易翻车的地方。容器默认的共享内存上限只有 64MB，observer 需要更大的共享内存段，启动时会直接报空间不足。我们把宿主机上的共享内存调大到 2G 之后，observer 才稳定跑起来，之前那种随机的租户资源不足错误也随之消失。

本地环境把数据库固定成 test，租户留空走默认租户。知识库场景通常不需要多租户隔离，但保留这个参数是为了将来部署到共享实例时不用改动代码结构，只需要把租户名填进环境变量。桥接服务从环境变量读取这些参数，浏览器端完全不感知数据库连接信息。

我们在桥接服务里把所有连接配置集中从一个配置对象读取，构造客户端时一次性传入。早期散落在各个模块里的硬编码 host 和 port 曾经导致过一次事故，本地跑通的脚本在测试环境因为连错租户而把演示数据写进了别人的库。

排查连接问题时我们习惯按这个顺序看：先看客户端报的具体错误码，再看服务端的 observer 日志，最后才看系统层面的资源水位。绝大多数连不上其实不是端口问题，而是租户或数据库名写错，或者初始化时序没等够，按这个顺序能少走很多弯路。
