# 连接池、超时与重试策略

seekdb 是无状态的分布式数据库，客户端连的是接入层地址，真正的数据读写由接入层转发给 observer。我们的架构里连接始终由 Node 侧桥接服务持有，浏览器只和本地 HTTP 接口打交道，不直连数据库。这一点必须坚持，否则数据库凭证会随前端包一起分发出去。

我们给客户端加了连接池，把空闲连接数和最大连接数都设成 8。知识库的写入是突发式的，平时查询稀疏，如果每次请求都新建连接，光是握手和鉴权就把延迟拉到了几十毫秒，客户端观测到的耗时里数据库连接会占到将近一半。

超时设置分三层：连接超时 3 秒，查询超时 15 秒，导入这类长请求单独放宽到 120 秒。关键在于查询超时要设得比客户端的 HTTP 超时短，否则服务端还在跑，用户那边的请求已经先断开了，日志里就会出现一堆无法归因的慢查询。

重试只对可重试错误开启，包括连接被重置和租户资源暂时不可用。写操作重试必须保证幂等，所以我们所有的写入都走覆盖语义，重复提交不会产生重复行。这一点在导入大文件时尤其重要，因为中途断网重传的概率不低。

重试次数控制在 2 次，每次之间用指数退避加一点随机抖动，避免多个前端同时重连把刚恢复的服务再次压崩。抖动幅度我们取了基准延迟的两成左右，经验上足够打散同步重试，再大就会明显拖慢正常请求。

排查连接问题时先看池子的耗尽情况。如果活跃连接长期贴着上限，说明上游某个接口的响应变慢了，把连接占住不放。我们最终把查询接口的数据库超时从 15 秒降到 8 秒，宁可快速失败让前端重试，也不要把连接池拖死。

还有一点经验是不要在请求处理里做长事务。批量导入我们拆成若干小批，每批独立提交，这样任何一个批次失败时不需要回滚整批数据，重试的粒度也小得多，失败恢复的等待时间从分钟级降到了秒级。
