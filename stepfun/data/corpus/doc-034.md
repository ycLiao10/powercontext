# RRF 融合的公式与 rank_constant

RRF 是 Reciprocal Rank Fusion 的缩写，思路非常朴素：只看每一路召回里的排名，不看分数本身，把多路的排名换算成一个融合分数。

公式是每个文档的分数等于所有召回路里 1 除以 k 加上它的名次，再对所有路求和。k 就是 rank_constant，常见默认值是 60。名次从一开始计，所以排在第一位的文档贡献是 1 除以 61。

这个常数的存在是为了压制头部的优势。1 减去 1 再除以 60 和 1 减去 2 再除以 60 的差距本来并不大，乘上常数之后差距被整体压小，两路都排在第一的文档不会仅仅因为多一路命中就碾压其它文档。

我们的配置是 rankConstant 取 60，rankWindowSize 取 100。窗口大小决定了每一路取多少条候选参与融合，它直接影响到融合的召回上限：某篇文档如果在两路都排在第一百名以后，它根本进不了候选池。

参数名在 SDK 里写作 rank_constant 和 rank_window_size，在生成 SQL 的接口里是一对驼峰形式的字段名。两边都出现过，写文档的时候要注明对应关系，不然很容易配错。

RRF 最大的优点是它完全不依赖两路分数的量纲。向量路的距离值落在零到二之间，全文路的 BM25 分数可能是十几甚至上百，直接加权相加需要先做归一化，而归一化方法的选择又会引入新的不确定性。

RRF 的代价是丢掉了分数的绝对信息。两份同样排在第五名的文档，一个和第一名的差距极小，另一个差得很远，RRF 分不出这个区别。对我们的场景这个损失可以接受，因为最终展示的是一个列表，而不是需要按阈值做判断。
