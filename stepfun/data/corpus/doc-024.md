# vsag 库与原生 HNSW 实现的差异

向量索引建表时有个 lib 参数，用来指定底层图索引的实现。我们的配置里写的是 vsag，这是 seekdb 默认推荐的实现；同名的 HNSW 算法在别的库里有自己的原生实现，两者的参数语义和性能特征并不完全一样。

选 vsag 的直接原因是它是当前版本测过的一组默认推荐实现。我们对比过自研实现和 vsag 在同一份中文语料上的表现，召回差距在噪声范围内，但 vsag 的构建速度明显更快，导入时用户等待的时间更短。

参数名上也有细微差别。社区版文档里常见的写法是 m 和 ef_construction，在 seekdb 的配置对象里对应的是 hnsw 段下的同名字段。搬配置的时候要按字段名一一对照，不能照抄 SQL 里的位置参数。

底层实现差异最直观的影响是内存布局。vsag 对邻居做了紧凑编码，边上不存浮点距离而是只存节点编号，需要时再算。这让图的常驻内存比朴素实现低了两成左右，在我们的规模上就是几 MB 的差别，感知不明显，但数据量上一个数量级之后就会变得可观。

我们不打算自己实现图索引。理由很简单：参数调优、内存布局、删除标记这些都要靠大量实测来验证，而我们要把精力留给检索链路本身。用一个被验证过的实现，然后把参数调好，比自己写一个更可靠。

最后一点提醒是升级路径。更换 lib 或者底层索引版本意味着整表重建，召回曲线也会跟着变，所以每次换实现都要重跑一遍质量评测，不能凭感觉认为差不多。
