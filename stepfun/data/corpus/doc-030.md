# 集合命名规范与生命周期管理

集合名不只是标签，它承担着路由、隔离和清理三件事，所以命名规则必须能从中读出这些信息。

我们的规则是 kb 加模型短名，中间用下划线连接。模型短名从模型标识里截取并规范化，去掉所有非法字符。名字短的好处是人能读懂，出问题时能直接对上库里的对象。

精度不进集合名。不同精度的向量可以放在同一个集合里，因为它们回答的是同一个问题。评测时我们把精度的区别放在评测脚本自己拼的集合名里，和线上的命名规则分开，避免两套规则互相污染。

命名规范只在客户端和注册表里维护一份。服务端收到集合名之后不做任何改写，这样出问题时能确定地判断名字是哪里来的。

生命周期分四个阶段：创建、写入、归档、清理。创建在第一次导入时发生，重复执行是幂等的。写入阶段只增不改，写入用 upsert 保证重复导入不产生重复行。

归档是很少用到但必须存在的阶段。实验性质的集合在一段时间不用之后，先改名加上归档后缀，把流量切走但保留数据，确认没问题再删除。

清理是最后一步，也是最容易做错的一步。删除集合不会删除底层物理表，旧表会带着向量数据一直留在库里。我们加了一条清理流程：删除集合之后按前缀扫一遍表，把同名不同 id 的孤儿表一并删掉。

删除之前必须确认表名。直接用通配删除是不可取的，前缀相同但用途不同的表会被误删，而误删的代价远高于多花几分钟手工确认。

另外还有一个隐性的生命周期：墓碑节点。反复删除再导入同一批文档，索引里的墓碑会累积，内存占用只增不减。所以频繁重建的集合，不如直接新建一个干净的集合再导入。
