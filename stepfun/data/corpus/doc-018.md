# 计时口径、分阶段耗时与统计量

性能数字如果口径不清楚，就没有任何可比性。我们把这套口径固定下来写进笔记，避免每次测出来的东西含义不同。

第一个原则是区分冷启动和热路径。模型加载属于冷启动，它包含权重读取、解析和会话创建；推理属于热路径，只计算实际的计算时间。这两个数字差两个数量级，混在一起报会严重误导。

第二个原则是分段计时并且分段可加。端到端耗时拆成查询向量化、库内检索和两者之和，三段的时间戳都取自浏览器的高精度计时器。端到端不是另外测的，而是由前两段相加得到，这样三者的数字永远自洽。

库内检索这一段的口径是从浏览器发出请求到拿到响应，包含网络往返。我们特意不把它定义成服务端执行时间，因为那需要服务端配合埋点，跨语言对时反而更容易出错。

第三个原则是报中位数而不是平均值。平均值会被偶发的长尾拉高，而用户感知的是中间水平。我们同时保留 p90 和最小值，最小值反映的是没有其它负载干扰时的真实能力。

样本量我们定在二十次以上。低于二十次，中位数的波动会盖过配置之间的差异，测了也是白测。

预热是计时前的必要步骤。正式采样之前先跑一次完整查询，把连接、缓存和图形管线都热起来。我们观察过未预热的第一次采样比后续高出一倍，直接把它算进中位数会严重低估性能。

跨设备可比性是最需要小心的。不同显卡、不同浏览器版本、不同精度的数字不能直接横向比较，必须在每台设备上重新跑完整的配置矩阵。我们记录的每条结果都带着环境信息，包括浏览器版本、CPU 型号和线程数。

还有一条是记录实际生效的配置。请求 WebGPU 但被降级成 WASM 的情况必须如实记录成 WASM，否则报表里会出现一个并不存在的 GPU 数字。
