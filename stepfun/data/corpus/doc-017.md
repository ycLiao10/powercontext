# 多数派副本与数据可靠性边界

OceanBase 的每个分区都靠 Paxos 协议维持多副本一致，写入必须获得多数派确认才算提交。这意味着单副本故障不会丢数据，但也意味着少数派存活时该分区不可写。

我们把副本数设成三，在两台机器上各放一份的情况下，任何一台宕机写入都还能继续。这个冗余的代价是每次提交要多一轮网络往返，写吞吐比单副本低三成左右，对知识库场景可以接受，因为导入是突发式的，平时几乎没有并发写入。

和普通关系库最不一样的地方是，提交成功和数据落盘是两件事。多数派确认代表数据已经进了日志流并被多数派持有，但还没有写到磁盘。这个窗口期如果整机断电，数据会丢；不过只要多数派中还有任一节点活着并把日志刷盘，数据就能恢复。

我们遇到过一次宿主机意外断电，恢复之后集合的记录数比断电前少了最后一批。当时达成的结论是要接受这个语义，不要在文档里承诺强持久化。导入流程因此被设计成可以重复执行，幂等 upsert 保证重放不会产生重复行。

多数派组的成员列表是可以调整的，加副本或者减副本都要走一轮成员变更流程，变更期间该分区的提交会短暂阻塞。我们的做法是把成员变更安排在低峰期，并且一次只动一个分组，避免多个分组同时变更把提交延迟叠加起来。

监控上我们主要看两件事：日志流的写入延迟和多数派组的状态。前者反映提交是不是在变慢，后者反映是不是有副本长期掉线。副本掉了却没有及时补齐，等于把冗余悄悄降级成了少数派，这比单点故障更值得警惕。
