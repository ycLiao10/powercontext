# 静态资源与模型文件的缓存策略

浏览器端的缓存分两类，一类是 HTTP 缓存管模型和运行时文件，另一类是应用内的内存缓存管已经算好的结果。两类的失效逻辑完全不同，混在一起会很难排查。

模型权重的缓存靠 HTTP 头。我们给模型目录的文件设长缓存，权重文件名里带内容哈希，内容变了文件名就会变，不会出现新旧混用。运行时文件同理。

模型目录本身需要是不带哈希的，因为 Transformers.js 是按固定的相对路径去请求 tokenizer 和配置文件的。这些小文件我们用短缓存甚至协商缓存，保证换模型版本后能及时拿到新的。

应用内缓存我们只做了一样东西：同一段文本的向量。导入语料时如果重复导入同一批文件，向量可以直接复用，不用重算。缓存键是文本内容加上模型标识和精度，三者有一个变了缓存就失效。

我们没有缓存检索结果。这个决定在低频场景下没什么损失，但理由必须说清楚：检索结果依赖库里的实时数据，缓存会让用户看到过期的命中结果，而知识库场景里搜到一篇已经被删掉的文档是很糟糕的体验。

跨源隔离相关的响应头不能缓存，因为它们影响运行时行为，我们给的是 no-store。

还有一点是不要给 HTML 入口页设长缓存。前端升级后如果入口页被缓存，用户会拿着旧的入口去加载新的静态资源，版本对不上，报出一堆看不懂的错误。
