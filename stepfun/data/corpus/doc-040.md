# WebGPU 与 WASM 后端的选择和降级

我们支持两种推理后端，WebGPU 和 WASM。WebGPU 走显卡，吞吐高很多；WASM 跑在 CPU 上，兼容性最好但慢。默认策略是优先 WebGPU，拿不到就自动降级到 WASM。

降级判定不能只看 navigator.gpu 是否存在，必须真的去请求一次 adapter 并拿到对象才算可用。有些环境里 gpu 对象存在但 adapter 为空，常见原因是显卡驱动太旧或者被安全策略禁用了。我们最初的实现只做了存在性检查，结果在那些机器上直接抛错而不是降级。

WASM 和 WebGPU 的实测差距比想象中大。同一批一千二百篇文档，WebGPU 上向量化用了九秒，WASM 上用了四十多秒，接近五倍。差距主要在批量吞吐上，单条查询的差距要小得多。

不过 WebGPU 有一个反直觉的问题：首次编译着色器很慢。第一个 batch 可能比 WASM 还慢，因为 GPU 管线要现场编译。跑到第三个 batch 之后才追上来，所以界面上的进度条不能假设第一批就快。

精度选项也和后端绑定。WebGPU 支持 fp16、fp32 和 q8，WASM 只支持 q8 和 fp32，fp16 在 WASM 上没有对应的实现。我们的默认值策略是 WebGPU 用 fp16，WASM 用 q8，因为 fp16 在显卡上既快又小，而 WASM 上 INT8 的收益最大。

我们还在界面上把显卡信息显示出来，包括厂商和架构。这在排查性能问题时很有用：同一台机器上换一个驱动版本，吞吐就可能变了十个百分点，光看"降级到 WASM"这四个字是解释不通的，必须看到具体适配器信息才查得下去。

界面上必须显示实际使用的后端，不能显示用户请求的那个。我们见过用户以为自己跑在显卡上，其实早就降级了，这个信息不展示出来就没办法解释性能差异。
